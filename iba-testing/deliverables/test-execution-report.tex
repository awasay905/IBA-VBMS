\section{Executive Summary}

\subsection{Overview}
This document serves as the official Test Execution Report for the first execution cycle of the IBA Campus Facility Booking System. The test suite was executed against the local testing environment consisting of a React frontend, NestJS backend, and an isolated Supabase PostgreSQL instance. Testing covered three distinct layers: unit testing of core services, integration testing of REST API endpoints, and end-to-end (E2E) automated browser workflows (via Playwright).

\subsection{Summary of Test Run Performance}
The overall test execution yielded mixed results, demonstrating high stability at the unit level but uncovering critical blocker defects during integration and end-to-end testing phases:
\begin{itemize}[noitemsep,topsep=3pt]
    \item \textbf{Total Test Cases Run:} 124 (39 Unit, 43 Integration, 42 E2E)
    \item \textbf{Passed Tests:} 108 (39 Unit, 34 Integration, 35 E2E)
    \item \textbf{Failed Tests:} 16 (0 Unit, 9 Integration, 7 E2E)
    \item \textbf{Overall Pass Rate:} 87.09\%
\end{itemize}

\subsection{Release Recommendation}
Based on the exit criteria defined in Section 9.2 of the Master Test Plan, the system is \textbf{not yet eligible for release}. The exit criteria require a minimum of a 95\% test pass rate and a 100\% resolution of Severity-1 (Critical) defects. This cycle has left four critical Severity-1 defects active, alongside several Severity-2 issues, primarily involving the database architecture and validation constraints.

\section{Failure Analysis and Technical Insights}
During this execution cycle, several distinct failure patterns were captured by the testing harness. This section links those failures directly back to code-level root causes.

\subsection{Unconditional DB Unique Constraint Blockers (DEF-002)}
The failure of TC-BOOK-009 (Concurrency) and TC-PO-004 (Conflict Resolution) is caused by a structural database flaw. In \texttt{supabase-schema.sql}, the unique constraint on the bookings table is declared as:
\begin{verbatim}
UNIQUE (room_id, date, slot_id)
\end{verbatim}
Because this constraint is unconditional, the database blocks any entry sharing a slot, regardless of status. Consequently, two students cannot submit concurrent pending requests for the same room and slot, which prevents the Program Office from ever receiving multiple pending options. Furthermore, once a booking is cancelled or rejected, that slot can never be re-booked without triggering a database violation (yielding an unhandled \texttt{500 error}).

\subsection{Hardcoded State Mismatch on Cancellation (DEF-001)}
The tests TC-CANCEL-001 and TC-CANCEL-005 failed because of a mismatch between the expected and received status payload. The test expects a status of \texttt{"cancelled"} upon cancellation, but received \texttt{"rejected"}. As verified in \texttt{bookings.service.ts}:
\begin{verbatim}
async cancel(id: string, requesterId: string, requesterRole: string) {
    ...
    return this.updateStatus(id, 'rejected', requesterId); 
}
\end{verbatim}
By routing cancellations to the rejection workflow, the application overwrites the audit history and returns incorrect metadata to the client.

\subsection{Missing DTO Range Validations (DEF-010)}
Test case TC-BOOK-004/7 failed because the API endpoints do not gracefully reject out-of-bounds slot IDs (such as \texttt{slot\_id: 0} or \texttt{slot\_id: 8}). Instead of returning a \texttt{400 Bad Request}, the backend throws an unhandled \texttt{500 Internal Server Error} because the invalid ID directly violates the foreign key constraint on the database. The \texttt{CreateBookingDto} in \texttt{bookings.service.ts} only checks if the input is an integer but fails to restrict the range to $[1, 7]$.

\subsection{Audit Trail Omissions (DEF-015)}
During TC-DATA-001, the integration runner fetched a newly approved booking from the API expecting to verify the reviewer’s identity. However, the assertion failed because the returned payload was missing the \texttt{reviewed\_by} attribute entirely. This is due to an explicit omission within the SQL SELECT projection string in \texttt{bookings.service.ts}, which prevents the audit trail from being displayed on the frontend.
