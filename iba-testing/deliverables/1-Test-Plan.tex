\section{Introduction}

\subsection{Purpose}

This Test Plan defines the overall testing strategy, scope, objectives, resources, schedule, and test cases for the IBA Campus Facility Booking System. The document is the primary reference for all testing activities carried out by the test team as part of the Software Testing course project.

\subsection{Background}

The Institute of Business Administration (IBA) currently manages campus facility bookings(CFBS) through informal, manual methods including emails, physical registers, and verbal coordination. This leads to double-bookings, scheduling conflicts, and a lack of real-time visibility across the campus.

The platform addresses these issues by providing a centralised, web-based platform that supports three user roles: \textbf{Students}, \textbf{Program Office (PO)} staff, and \textbf{Administrators}. Students can request room bookings, the Program Office approves or rejects those requests, and Administrators manage the overall system configuration.

\subsection{Scope}

\textbf{In scope:}
\begin{itemize}[noitemsep]
  \item All nine feature areas from the SRS: Authentication, Room Booking, Booking Approval/Rejection, User Management (Admin), Room Management, Building Management, Booking Cancellation, Slot Blocking, and Real-time Availability
  \item Unit testing of individual backend controllers and service functions
  \item API-level integration testing of all REST endpoints
  \item End-to-end UI workflow testing via automated browser scripts
  \item Negative path testing, boundary value analysis, and equivalence partitioning
  \item Concurrency and conflict-detection testing (double booking, simultaneous slot requests)
  \item Role-based access control (RBAC) security testing
  \item Performance and load testing using free tools
  \item Data persistence and audit trail verification
  \item Frontend UX correctness: slot availability visibility, booking status indicators
\end{itemize}

\textbf{Out of scope:}
\begin{itemize}[noitemsep]
  \item Penetration testing beyond role-based access checks
  \item Production deployment and infrastructure testing
\end{itemize}

\section{Test Objectives}

The testing effort for CFBS aims to achieve the following objectives:

\begin{enumerate}[leftmargin=1.5em]

  \item \textbf{Verify Functional Correctness.}
  Confirm that all nine system features behave in accordance with the requirements defined in the SRS.

  \item \textbf{Ensure Booking Conflict Prevention.}
  Verify that the system correctly rejects booking requests that conflict with an already-approved booking for the same room, date, and time period --- including double-booking, blocked slots, and simultaneous requests from multiple students for the same slot.

  \item \textbf{Validate Role-Based Access Control.}
  Ensure that Students, Program Office staff, and Administrators can only perform actions within their authorised scope. Unauthorised actions must be blocked with appropriate error messages.

  \item \textbf{Confirm Booking Constraint Enforcement.}
  Validate that time slot restrictions (9~AM to 6~PM only), current-year date restrictions, and room-disabled states are properly enforced.

  \item \textbf{Confirm Frontend Availability Visibility.}
  Verify that the frontend communicates slot availability clearly before a student submits a request, not only after a conflict error is returned.

  \item \textbf{Validate PO Applicant Distinction.}
  Verify that the Program Office can distinguish between a student and a faculty/teacher applicant from the booking request details.

  \item \textbf{Validate Input Handling and Edge Cases.}
  Confirm that edge cases --- invalid credentials, past dates, zero capacity, duplicate ERP/username --- are handled gracefully with clear, non-sensitive error messages.

  \item \textbf{Assess User Notifications.}
  Confirm that the booking approval and rejection notification mechanism correctly informs the student of the Program Office decision.

\end{enumerate}

\begin{infobox}
\textbf{Success Criterion:} Testing is considered successful when all planned test cases have been executed, all Severity-1 (Critical) defects have been resolved and re-tested, and $\geq$90\% of Severity-2 (Major) defects are resolved prior to release.
\end{infobox}

\section{Test Strategy and Approach}

Testing for CFBS follows a risk-based, specification-driven strategy aligned with IEEE 829 and ISTQB principles. Higher-priority and higher-risk features authentication, room booking, and approval/rejection receive the most thorough coverage.

  \item \textbf{Regression Testing} --- re-executed after every defect fix

\section{Entry and Exit Criteria}

\subsection{Entry Criteria}

Testing of each module may begin only when all of the following conditions are satisfied:

\begin{itemize}
  \item The SRS has been reviewed by the team
  \item The feature under test is code-complete and deployed to the test environment
  \item Test data (user accounts, rooms, buildings) has been seeded in the test database
  \item The test environment (frontend, backend, database) has been verified as operational
  \item All Severity-1 (Critical) defects from the preceding test cycle have been resolved
\end{itemize}

\subsection{Exit Criteria}

Testing may be formally concluded when:

\begin{itemize}
  \item All planned test cases have been executed
  \item All Severity-1 (Critical) defects have been fixed, re-tested, and closed
  \item $\geq 90\%$ of Severity-2 (Major) defects have been resolved
  \item Test coverage is $\geq 95\%$ for all in-scope features
  \item UAT sign-off has been received from the project stakeholder
\end{itemize}
