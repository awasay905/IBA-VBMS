\section{Executive Summary}

\subsection{Overview}
This document serves as the official Test Execution Report for the first execution cycle of the IBA Campus Facility Booking System. The test suite was executed against the local testing environment consisting of a React frontend, NestJS backend, and an isolated Supabase PostgreSQL instance. Testing covered three distinct layers: unit testing of core services, integration testing of REST API endpoints, and end-to-end (E2E) automated browser workflows (via Playwright).

\subsection{Summary of Test Run Performance}
The overall test execution yielded excellent results, demonstrating high stability across all layers of the test suite:
\begin{itemize}[noitemsep,topsep=3pt]
    \item \textbf{Total Test Cases Run:} 124 (39 Unit, 43 Integration, 42 E2E)
    \item \textbf{Passed Tests:} 124 (39 Unit, 43 Integration, 42 E2E)
    \item \textbf{Failed Tests:} 0
    \item \textbf{Overall Pass Rate:} 100.0\%
\end{itemize}

\subsection{Release Recommendation}
Based on the exit criteria defined in Section 9.2 of the Master Test Plan, the system \textbf{meets all automated test quality gates and is recommended for release}. All 124 test cases pass across unit, integration, and E2E levels, achieving a 100\% pass rate. Previously identified Severity-1 defects (DEF-001, DEF-002, DEF-003, DEF-004, DEF-007, DEF-010, DEF-015) have been resolved.

\section{Defect Resolution Summary} \label{sec:failures}
During this execution cycle, all previously identified defects were resolved. The following subsections document the root causes and the fixes applied.

\subsection{Conditional DB Unique Constraint Fix (DEF-002 --- Resolved)}
The failures of TC-BOOK-009 (Concurrency) and TC-PO-004 (Conflict Resolution) were caused by a structural database flaw. The unconditional unique constraint in \texttt{supabase-schema.sql} was replaced with a conditional partial index targeting only active bookings:
\begin{verbatim}
CREATE UNIQUE INDEX idx_active_bookings ON bookings (room_id, date, slot_id)
  WHERE (status IN ('pending', 'approved'));
\end{verbatim}
This allows multiple students to submit concurrent pending requests for the same slot and permits slot recycling after cancellation or rejection.

\subsection{Cancellation Status Fix (DEF-001 --- Resolved)}
The tests TC-CANCEL-001 and TC-CANCEL-005 were failing because the cancel handler in \texttt{bookings.service.ts} was routing to the rejection workflow with a hardcoded \texttt{'rejected'} status. The fix corrected the status string to \texttt{'cancelled'}:
\begin{verbatim}
async cancel(id: string, requesterId: string, requesterRole: string) {
    ...
    return this.updateStatus(id, 'cancelled', requesterId);
}
\end{verbatim}
Cancellations now correctly set the status to \texttt{cancelled}, preserving the distinction between rejections and cancellations in the audit log.

\subsection{DTO Range Validation Fix (DEF-010 --- Resolved)}
Test case TC-BOOK-004/7 was failing because the API accepted out-of-bounds slot IDs (such as \texttt{slot\_id: 0} or \texttt{slot\_id: 8}), causing an unhandled \texttt{500 Internal Server Error}. The \texttt{CreateBookingDto} was updated with \texttt{@Min(1)} and \texttt{@Max(7)} decorators, so invalid values are now rejected with a clean \texttt{400 Bad Request} validation response before reaching the database.

\subsection{Audit Trail Field Fix (DEF-015 --- Resolved)}
During TC-DATA-001, the integration runner was fetching booking records and asserting on the \texttt{reviewed\_by} field. The fix added \texttt{reviewed\_by} to the SQL SELECT projection string in \texttt{bookings.service.ts}, ensuring the reviewer's identity is returned in the API response and displayed correctly on the frontend audit trail.
